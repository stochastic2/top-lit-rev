Important limitation before applying
------------------------------------
THIS IS A STRUCTURAL MIGRATION, NOT A RUNNABLE PACKAGE CONVERSION.

The code currently uses flat imports, sibling entry-point paths and __file__
to locate other files. Markdown and figure builders use relative paths too.
Moving these files without follow-up changes will break some commands, imports,
tests, links and figure builders. The script reports this in preview and apply.
It deliberately avoids guessing replacements or modifying research source text.

Recommended sequence: review this layout first; then coordinate the actual moves
with a separate import/link/entry-point update and verification pass. Existing
saved-run snapshots must remain immutable; old source-tree hash comparisons will
naturally differ after any later source edits. Keep using the current layout
until that migration is ready. No simulations need to be run for this review.

Safety properties
------------------
* Default is PREVIEW, with no writes.
* All entries are checked before the first move: regular file, relative path,
  safe nonsymlink parents, unique source/destination, no existing destination.
* Only individual .py/.md files in the reviewed code/documentation roots qualify.
  Output directories, Git internals and path traversal are refused.
* Applying uses mkdir -p and mv -n, never rm, force, Git clean or Git reset.
  A move removes its old pathname while preserving the file and its contents;
  this is not a second backup copy of each file.
* SHA-256 is checked before and after every move.
* A fresh journal is written under reorganization-logs/. Each move's intent is
  recorded BEFORE the move, so a pending/interrupted entry can be distinguished.
* Undo is preview-only unless --apply is also supplied. It refuses collisions,
  changed contents, the wrong repository root and ambiguous file states.
* Undo leaves empty folders and every journal in place; it deletes nothing.
* A failure may leave a partial migration. Keep the journal and inspect/undo it.
  Do not run concurrently with another migration, source editor or simulation.
* No promise is made against disk failure, hostile concurrent filesystem changes
  or operating-system failure. The journal is not a substitute for a backup.
